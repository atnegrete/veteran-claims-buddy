# Hosting architecture

**Updated:** 2026-10-04

How the two web surfaces are hosted on Firebase, in dev and in prod, and the end-goal custom domains. `docs/page-navigation.md` stays the source of truth for what pages exist; this file is how they are served.

## The shape: two sites per environment

Each environment is **two separate Firebase Hosting sites** inside that environment's Firebase project:

1. **Marketing** — the static landing site. The public directory is `marketing-site/`, generated by `marketing-site/build.js`. This is the front door: home, how-it-works, pricing, the VA calculator, FAQ, support, and the legal pages. A "Veteran Login" control in the top-right links out to the app site's sign-in URL.
2. **App** — the Flutter web build. The public directory is `app/build/web`. It is a single-page app, so every path rewrites to `/index.html` and `go_router` handles routing.

A single Firebase project can hold many Hosting sites. We use two per project and address them with Hosting **targets** named `marketing` and `app`. The target names are stable across environments; only the underlying site ids and domains change.

## Site ids and URLs

| Environment | Target | Firebase site id | Default Firebase URL |
| --- | --- | --- | --- |
| Dev | `marketing` | `veteran-claims-buddy-dev` (the project's default site) | `https://veteran-claims-buddy-dev.web.app` |
| Dev | `app` | `veteran-claims-buddy-dev-app` | `https://veteran-claims-buddy-dev-app.web.app` |
| Prod | `marketing` | `veteran-claims-buddy-prod` (the project's default site) | `https://veteran-claims-buddy-prod.web.app` |
| Prod | `app` | `veteran-claims-buddy-prod-app` | `https://app` lives on the custom domain |

The default site (same id as the project) always exists. The second site (`-app`) must be created once with `firebase hosting:sites:create`.

## End-goal custom domains (after the domain is purchased)

The domain is `veteranclaimsbuddy.com`. A custom domain attaches to a specific Hosting **site**, independent of the site id.

| Domain | Attaches to site | Purpose |
| --- | --- | --- |
| `veteranclaimsbuddy.com` | prod `marketing` (`veteran-claims-buddy-prod`) | Public landing / static pages |
| `www.veteranclaimsbuddy.com` | prod `marketing` | Redirects to the apex |
| `app.veteranclaimsbuddy.com` | prod `app` (`veteran-claims-buddy-prod-app`) | The Flutter app |
| `dev.veteranclaimsbuddy.com` | dev `marketing` (`veteran-claims-buddy-dev`) | Dev landing |
| `app-dev.veteranclaimsbuddy.com` | dev `app` (`veteran-claims-buddy-dev-app`) | Dev app |

Connecting these is an owner step at launch (build-progress M9). Until then every surface uses its `.web.app` URL. The marketing landing's login button points at the matching app URL for that environment: in dev it points at the dev app's `.web.app` (or `app-dev.` once connected); in prod it points at `app.veteranclaimsbuddy.com`.

## How it is wired in the repo

- **`firebase.json`** has a `hosting` array with two entries, one per target. `marketing` serves `marketing-site/` (ignoring `build.js` and `*.test.js`). `app` serves `app/build/web` with a catch-all rewrite to `/index.html`.
- **`.firebaserc`** maps the `marketing` and `app` targets to the site ids above, per project. This is what `firebase target:apply` would otherwise write; it is pre-filled so a deploy just works once the sites exist.
- **`marketing-site/build.js`** is environment-aware. URLs default to the production domain, so committed pages and `marketing-site/site.test.js` stay on production. `npm run build:marketing` writes that HTML, then compiles `marketing-site/css/site.css` from `marketing-site/styles/input.css`. A dev build overrides the URLs:
  - `npm run build:marketing` — production URLs (the default).
  - `npm run build:marketing:dev` — dev `.web.app` URLs.
- **The Flutter web build** comes from `fvm flutter build web --dart-define=APP_ENV=<dev|prod>` and lands in `app/build/web`. Web has no `--flavor`, so the environment is passed as the `APP_ENV` dart-define, which `app/lib/app/app_environment.dart` reads. Mobile still uses `--flavor`.

## Deploy — dev

One-time, create the dev app site (the marketing site already exists as the default site):

```bash
npx -y firebase-tools@latest hosting:sites:create veteran-claims-buddy-dev-app --project dev
```

From the repo root:

- `npm run build:deploy:marketing:dev` builds the marketing pages with dev URLs and deploys that site.
- `npm run build:deploy:app:dev` builds the Flutter web app for dev and deploys that site.
- `npm run build:deploy:hosting:dev` builds both, then deploys both.

Deploy without rebuilding with `npm run deploy:marketing:dev`, `npm run deploy:app:dev`, or `npm run deploy:hosting:dev`.

Success: the command prints a `Hosting URL` for `veteran-claims-buddy-dev`, `veteran-claims-buddy-dev-app`, or both.

## Deploy — prod (later, owner gate)

One-time, create the prod app site:

```bash
npx -y firebase-tools@latest hosting:sites:create veteran-claims-buddy-prod-app --project prod
```

From the repo root, `npm run build:deploy:marketing:prod`, `npm run build:deploy:app:prod`, or `npm run build:deploy:hosting:prod`. Those use production URLs. Connecting the custom domains is build-progress M9.

## Best-practice notes

- One project, multiple sites, addressed by target names. Do not create a second Firebase project just to host a second site.
- A custom domain binds to a site, so the dev/prod split and the marketing/app split are both just site choices. Moving a domain later is a console action, not a code change.
- The app site must have the SPA rewrite, or deep links (for example `/cases/123/conditions`) return 404 on refresh.
- Keep secrets and the real domain out of the committed marketing build; dev URLs come from the dev build script, not committed files.
